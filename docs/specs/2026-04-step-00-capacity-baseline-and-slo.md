# Step 00：容量基线、SLO 与压测口径统一

## 标题

在改架构前，先统一“1000 在线”的业务定义、性能目标、压测口径和观测字段。

## 背景

- “1000 在线”并不等于“1000 人同时发起图/视频生成”。
- 如果不先定义负载画像，后面的扩容动作很容易变成拍脑袋。
- 当前平台已有健康检查，但缺少统一的 SLI/SLO、容量阈值和标准压测剧本。
- 平台未来会接入更多模型厂商与更多模块，因此必须把“平台承载能力”和“外部供应商配额能力”拆开定义。

## 目标

- 明确当前确认的目标工作负载画像
- 定义 SLI / SLO / 错误预算
- 定义 staging 压测场景与通过门槛
- 定义“平台侧指标”和“供应商侧指标”的边界
- 为后续每一步改造提供可比较的前后数据

## 非目标

- 本步骤不改业务存储架构
- 本步骤不直接引入 Redis / PostgreSQL / 队列
- 本步骤不默认对真实供应商接口做大规模压测

## 用户流 / 角色

- 运维/开发者需要回答：
  - 1000 在线里有多少活跃用户？
  - 同时提交任务的峰值是多少？
  - 允许的排队时间是多少？
  - 哪些接口必须“快”，哪些接口可以排队？
  - 哪些瓶颈属于平台，哪些瓶颈属于供应商配额/预算？

## 方案对比

### 方案 A：先改再测

- 优点：速度快
- 缺点：没有基线，后续无法证明优化是否有效

### 方案 B：先建立容量口径和观测字段

- 优点：每一步都有可比较指标
- 缺点：前期文档和测试准备工作更多

### 推荐

- 选择 **方案 B**

## 当前确认的工作负载目标

### 当前确认目标：W2

本轮确认按路线图中的 **W2** 打底：

- **1000 在线用户**
- **200~300 活跃操作用户**
- **30 个并行任务提交**
- **300~500 个正在观察状态的任务**

### 业务解释

- “在线用户”指已登录、保持页面打开、可能触发轮询或订阅的用户。
- “活跃操作用户”指在一个统计窗口内真实执行创建、编辑、提交、查看结果等操作的用户。
- “并行任务提交”指在短时间窗口内同时进入“提交生成任务”路径的请求数，不等于供应商一定会同时开始执行。
- “观察状态的任务”指用户已经提交任务，前端仍在通过轮询或 SSE 关注任务变化。

### 系统语义

- 在 **W2** 下，**任务排队中是允许且正常的状态**。
- 在 **W3** 类场景下，平台目标是“稳定承接并排队”，而不是承诺所有任务瞬时开始执行。

## 平台指标边界

### 平台必须负责的指标

- 登录与鉴权成功率
- 读接口延迟
- 任务提交接口延迟
- 任务状态对前端可见的延迟
- 队列积压与 Worker 占用
- 系统级错误率

### 不应直接作为平台硬门禁的指标

- 真实供应商端生成完成总耗时
- 供应商排队时长
- 供应商配额耗尽后的等待时长
- 单次生成成本

说明：

- 以上指标仍然要**记录**，但默认不作为 Step 00 的平台承载硬门槛。
- 压测默认先关注“平台是否能稳定接住请求、记录任务、展示状态、正确排队”，而不是对真实 DashScope 或其他供应商做压力轰炸。

## 推荐定义

### 核心 SLI

- 登录接口成功率
- 普通读接口 P95 / P99 延迟
- 任务提交接口成功率与 P95 延迟
- 任务状态变更对前端可见延迟
- 系统级 5xx 错误率
- 队列长度与任务积压情况
- Redis / PostgreSQL 可用性（引入后）

### 第一版 SLO

- 普通读接口：`P95 < 300ms`
- 登录/鉴权接口：`P95 < 500ms`
- 任务提交接口：`P95 < 800ms`
- 任务状态变更对前端可见：`P95 < 3s`
- 系统级错误率：`< 1%`

### 错误预算口径

- 在 staging 压测场景下：
  - 非供应商原因导致的系统级失败，应低于 `1%`
  - 不把供应商配额耗尽、供应商 5xx、外部网络抖动直接算作平台错误预算消耗
- 但供应商错误必须被独立分类记录，不能混进“未知失败”

## 标准压测场景

### 场景 S1：纯读流量

- 目标：验证登录后列表、详情、配置类读取在高在线下是否稳定
- 特征：
  - 以列表/详情/元数据读取为主
  - 不引入真实任务提交
  - 用于建立最基础的 API 读延迟基线

### 场景 S2：读写混合流量

- 目标：验证在常规活跃用户操作下，读写混合是否稳定
- 特征：
  - 包含登录、项目列表、实体创建/更新、工作室配置变更
  - 不要求真实供应商生成完成
  - 重点观察 API 延迟、文件 I/O 压力与错误率

### 场景 S3：任务提交 + 状态观察

- 目标：验证任务提交、排队、状态查询/推送链路是否可承载
- 特征：
  - 包含最多 `30` 个并行任务提交
  - 包含 `300~500` 个正在观察状态的任务
  - 在当前轮询架构下先记录状态查询放大；后续 Step 05 再复用同场景对比 SSE 收益

## 实现边界

- 前端：
  - 识别高频轮询页面
  - 记录当前任务状态更新方式
  - 不把前端页面真实渲染耗时混进 API 承载结论
- 后端：
  - 补齐请求 ID、任务 ID、用户 ID 追踪
  - 为压测准备稳定接口和测试账户
  - 区分平台失败与供应商失败
- 基础设施：
  - 准备 Linux staging 环境
  - 在 Step 01 完成前，允许先以脚本生产模式建立基线
  - Step 01 完成后，必须在 Compose 路径复跑同一套场景

## 可观测性

本步骤必须先统一以下字段：

- `request_id`
- `user_id`
- `task_id`
- `provider_request_id`
- `worker_id`
- `deployment_version`
- `loadtest_run_id`
- `scenario_name`

要求：

- 后续任何扩容步骤都不能绕过这些字段
- 真实供应商错误必须保留原始错误分类或错误码
- 压测结论必须能关联到具体 Git 版本和部署版本
- HTTP 链路至少应暴露：
  - `X-Request-ID`
  - `X-Deployment-Version`
