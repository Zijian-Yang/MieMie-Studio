# Step 04：核心业务状态逐步迁往 PostgreSQL

## 标题

把最关键、最常查询、最需要一致性的业务状态从 JSON 文件迁到 PostgreSQL。

## 背景

- 当前 `StorageService` 通过大量 `glob("*.json")` 和逐文件反序列化完成查询。
- 这种模式在数据规模增长、多用户并发、任务索引查询下会持续恶化。
- 但一次性全量迁移风险太高。

## 目标

- 建立 repository / storage gateway 抽象
- 让核心实体逐步迁往 PostgreSQL
- 保持可回退、可比对、可回填

## 非目标

- 本步骤不要求一次迁完所有 JSON
- 本步骤不要求历史 JSON 立即删除

## 方案对比

### 方案 A：一次性切 PostgreSQL

- 优点：最终形态最直接
- 缺点：风险高、回滚难、测试面太大

### 方案 B：抽象存储层 + 双写 + 回填 + 读切换

- 优点：
  - 风险可控
  - 可逐实体推进
  - 易于回滚
- 缺点：
  - 迁移期间复杂度更高

### 推荐

- 选择 **方案 B**

## 推荐数据库

### PostgreSQL vs MySQL

- **推荐 PostgreSQL**
- 原因：
  - 更适合复杂查询和 JSONB 过渡
  - 事务、索引、约束能力更适合作为平台核心状态库
  - 对任务状态、配置快照、迁移阶段兼容数据更友好

### 2026-06-06 设计更新

- 部署形态选择 **Compose 内 PostgreSQL**，不走 SQLite 中转。
- JSON 可以在过渡期继续作为主数据源，但最终核心业务状态全部迁入 PostgreSQL。
- 过渡期必须保留回填、双写、对账和读切换开关。
- 升级优化总计划见 `docs/plans/2026-06-06-postgres-upgrade-optimization-plan.md`。
- 第一实施域选择视频工作室任务索引/任务状态；项目表、媒体库 metadata 和其他 domain 后续分批迁移。

## 推荐迁移顺序

1. 任务索引与任务状态表
2. 项目表
3. 角色 / 场景 / 道具 / 分镜首帧
4. 视频 / 图库 / 媒体库
5. 测评数据集 / suite / run

## 为什么先迁任务和项目

- 它们对查询一致性和列表性能影响最大
- 也最容易成为多节点协作时的状态源

## 实施粒度（建议）

1. 建立 repository 接口
2. 为任务/项目新增 PostgreSQL 实现
3. 回填历史数据
4. 双写并对账
5. 读切换
6. 扩展到下一类实体

## 数据迁移原则

- 每个实体都要有：
  - schema 定义
  - 迁移脚本
  - 校验脚本
  - 回滚策略
- 不允许“只写迁移脚本，不写对账脚本”

## 实现边界

- 前端：
  - 不应感知底层存储切换
- 后端：
  - 通过 storage gateway 屏蔽文件/数据库差异
- 基础设施：
  - PostgreSQL 备份、恢复、连接池、权限分离

## 可观测性

- PostgreSQL 连接池
- 慢查询
- repository 命中源（file / pg）
- 双写失败与对账差异

## 验收标准

- 至少一类核心实体完成：
  - PostgreSQL 写入
  - 列表查询读切换
  - 与历史数据对账通过
- 回滚路径已验证

## 讨论重点

- 你更希望先迁：
  - 任务状态
  - 还是项目主数据
- 我的建议是先迁任务状态，因为扩容收益最大、用户可感知最明显。
