# Step 01：Linux 生产运行时与边缘层收敛

## 标题

先把生产部署模型从“开发机思路”纠正为“Linux 服务器思路”，建立清晰的 API、静态资源、反向代理和部署边界。

## 背景

- 当前 `run.sh` 已能启动生产模式，但整体仍偏“单机进程启动脚本”。
- 在 1000 在线目标下，边缘层、静态资源、超时、压缩、连接复用、日志落盘策略都不能继续依赖应用进程默认行为。
- 项目用户的服务器环境差异较大，很多人会通过宝塔、自装 Nginx / Caddy 或云负载均衡来接入应用。

## 目标

- 明确 Linux 生产部署拓扑
- 确定 API、静态资源、TLS、反向代理的责任边界
- 确定第一阶段生产交付形态
- 明确“项目只提供应用监听端口，反向代理由用户自行选择和托管”的边界

## 非目标

- 本步骤不引入 PostgreSQL 业务迁移
- 本步骤不引入 Worker 队列
- 本步骤不在仓库内维护特定 Nginx / 宝塔 / Caddy 配置作为平台交付物

## 方案对比

### 方案 A：继续以脚本模式部署应用（`run.sh install` + `./run.sh start --prod`）

- 优点：
  - 对现有用户最友好
  - 上手门槛最低
  - 与当前仓库现状最接近
- 缺点：
  - 当 Redis / PostgreSQL / Worker 逐步加入后，应用侧依赖管理会越来越分散
  - staging 和 production 一致性较弱
  - 对后续标准化扩容帮助有限

### 方案 B：Linux 上 Docker Compose 编排应用侧服务，反向代理仍由用户自管

- 优点：
  - 更接近标准生产形态
  - API / Redis / PostgreSQL / Worker 后续都容易纳入同一套编排
  - 便于 staging 和 production 保持一致
  - 不强绑定具体反向代理实现，用户可以继续用宝塔、Nginx、Caddy、云负载均衡
- 缺点：
  - 需要维护镜像、Compose、部署文档
  - 团队需要理解容器、镜像、volume、network 等基础概念

### 方案 C：systemd / 手工安装多个进程与依赖

- 优点：
  - Linux 原生
  - 没有容器学习门槛
- 缺点：
  - 当服务逐渐拆成 API / Worker / Redis / PostgreSQL 组合后，环境复制与依赖管理会更散
  - 文档、故障排查和升级成本会持续上升

### 方案 D：直接 Kubernetes

- 优点：标准化程度高
- 缺点：对当前阶段过重

### 推荐

- 采用“双路径、单边界”策略：
  - **推荐生产参考路径：方案 B（Docker Compose）**
  - **保留低门槛兼容路径：方案 A（脚本模式）**
- 不推荐把方案 A 和方案 B 都做成完全等价、长期并行演进的两套系统；应保持：
  - 应用运行契约一致
  - 运维责任边界一致
  - 只是打包和启动方式不同

## 推荐细节

### 第一阶段生产形态

- Linux 服务器
- 项目对外只要求“应用监听一个 HTTP 端口”
- 反向代理由部署者自行选择和托管：
  - 宝塔里的 Nginx
  - 自建 Nginx / Caddy
  - 云厂商 ALB / SLB / CDN
- Docker Compose 模式下，仓库负责：
  - API 服务
  - Worker 服务（后续步骤引入）
  - Redis / PostgreSQL 等应用侧依赖（按步骤引入）
- 脚本模式下，仓库继续负责：
  - Python / Node 依赖安装
  - 前后端构建与启动
  - 单机应用进程运行

### 平台对反向代理的最小要求

- 能把外部请求转发到应用监听端口（默认可为 `8000`）
- 能透传 `Host`、`X-Forwarded-For`、`X-Forwarded-Proto`
- 能配置较大的请求体大小限制，覆盖图片/视频上传
- 能配置较长的读取超时，覆盖长任务提交与后续 SSE
- 当平台切到 SSE 后，不能对事件流做缓冲或过早断开

### 为什么不是 systemd-first

- systemd 本身没问题，但当服务开始拆成 API / Worker / Redis / PostgreSQL 依赖组合时，Compose 更适合统一管理。
- 如果用户明确不使用 Docker，仍可保留脚本部署作为兼容路径；但不建议继续扩展成“手工安装所有依赖 + 多服务 systemd 编排”的主路径。

### 为什么不是 Kubernetes-first

- 当前最关键的问题是状态和任务边界，不是调度编排本身。
- 先把服务模型理顺，再看是否需要 K8s，会更稳。

## 建议的反向代理职责

- TLS 终止
- Gzip / Brotli 压缩
- 静态资源缓存头
- API 超时与 body 大小限制
- 转发头透传
- 对 SSE 的连接保持配置

说明：

- 上述职责是“部署要求”，不是“仓库必须提供 Nginx 配置模板”。
- 仓库文档可以给出最小检查项和可选示例，但不把具体代理实现纳入平台交付边界。

## 实现边界

- 前端：
  - 生产静态资源路径与 API 路径分离
- 后端：
  - 健康检查与 readiness / liveness 边界清晰
  - 应用默认暴露单一监听端口
  - 不再把特定反向代理配置作为平台代码的一部分
- 基础设施：
  - Compose 文件（推荐路径）
  - 环境变量模板
  - Linux 部署说明
  - 脚本模式部署说明（兼容路径）
  - 反向代理最小要求说明，而非具体产品配置托管

## 可观测性

- 反向代理请求日志（具体实现由用户环境决定）
- API access/error log
- 部署版本号与 Git commit
- 健康检查、ready 状态、反向代理 upstream 错误

## 验收标准

- 在 Linux staging 环境至少有两种可验证路径：
  - `run.sh` 脚本部署可工作
  - Docker Compose 部署可工作
- 平台文档明确：用户可使用宝塔等自管反向代理，只需反代到项目端口
- 已形成“开发环境 vs 脚本生产模式 vs Compose 模式”差异文档
