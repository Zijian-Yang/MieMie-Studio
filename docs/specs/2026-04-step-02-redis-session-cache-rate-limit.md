# Step 02：Redis 会话、缓存与分布式限流

## 标题

先把最容易造成多 worker 不一致和文件热点竞争的状态迁到 Redis。

## 背景

- 当前会话依赖本地文件，鉴权链路每次请求都需要重新读取会话/用户数据。
- 当前限流是应用内默认配置，天然存在多 worker / 多实例不一致风险。
- 当前配置与热点状态没有统一缓存层。

## 目标

- 用 Redis 承载会话
- 用 Redis 承载分布式限流状态
- 为热点配置和任务状态查询建立缓存基础设施

## 非目标

- 本步骤不迁移核心业务实体到 PostgreSQL
- 本步骤不改长任务执行框架

## 方案对比

### 方案 A：JWT 无状态鉴权

- 优点：
  - 理论上减少服务端会话存储
- 缺点：
  - 登出、踢出、强制失效、细粒度会话管理更复杂
  - 当前平台已有 token 会话语义，切换成本高

### 方案 B：Redis 中保存 opaque session

- 优点：
  - 与当前 token 模式最接近
  - 支持登出、失效、TTL、后台管理
  - 多实例一致性好
- 缺点：
  - 引入 Redis 依赖

### 推荐

- 选择 **方案 B**

## 推荐细节

### 会话模型

- 登录成功后生成随机 token
- Redis 存：
  - `session:{token}` -> `user_id / created_at / expires_at / metadata`
- TTL 直接交给 Redis
- 用户登出、管理员失效、密码变更都可以主动删除

### 为什么不建议直接上 JWT

- 当前需求更像传统服务端会话，而不是跨系统单点登录。
- Redis 会话更适合小步迁移，并能支持未来的并发控制、设备会话管理。

### 缓存建议

- 缓存热点但不缓存权限结论太久
- 优先考虑：
  - 用户配置快读
  - 模型注册表
  - 任务详情短 TTL 缓存
- 不建议：
  - 长时间缓存用户可变业务数据，造成读旧

### 限流建议

- 用户级限流优先于 IP 级限流
- 登录/注册、任务提交、任务状态查询要分开限流
- 限流状态必须存 Redis，不能只存进程内

## 实施粒度（建议）

1. 先抽象 session store 接口
2. 增加 Redis session store
3. 双读：Redis 优先，文件会话兜底
4. 切写：登录/登出改写 Redis
5. 切读：鉴权主读 Redis
6. 限流状态切到 Redis
7. 再考虑热点缓存

## 实现边界

- 前端：
  - token 载体可以不变
- 后端：
  - auth middleware 改为读 Redis session store
  - 用户资料仍可先保留现有存储
- 基础设施：
  - Redis 高可用、备份、密码、网络白名单

## 可观测性

- Redis 连接数
- session 命中率
- 登录/鉴权失败分类
- 限流触发次数与类型

## 验收标准

- 多 worker / 多实例下登录、登出、过期一致
- 压测下鉴权链路不再主要受本地文件 I/O 影响
- 限流在多实例下结果一致
