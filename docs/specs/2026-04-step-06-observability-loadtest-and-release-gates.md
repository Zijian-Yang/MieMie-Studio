# Step 06：观测、压测、发布门禁固化

## 标题

把“能跑”升级成“可观测、可压测、可灰度、可回滚”的服务器级交付体系。

## 背景

- 架构改造如果没有统一门禁，很容易出现“局部变好、整体变坏”。
- 1000 在线目标不是通过主观感觉验收，而是通过数据验收。

## 目标

- 固化监控面板、日志字段、告警规则
- 建立标准压测脚本
- 定义每一步进入 `main` 的门禁

## 非目标

- 本步骤不新增核心业务功能

## 方案对比

### 压测工具：k6 vs Locust

#### k6

- 优点：
  - HTTP/SSE 场景友好
  - 指标输出清晰
  - 更适合做网关/API 基准
- 缺点：
  - 复杂业务流脚本不如 Python 灵活

#### Locust

- 优点：
  - Python 编写，复杂业务流更灵活
- 缺点：
  - 对 SSE 和一些前端式交互建模不如 k6 直接

#### 推荐

- **首选 k6**
- 如后续需要非常复杂的 Python 业务编排，再补 Locust

### 监控方案：自建 Prometheus/Grafana/Loki vs 云托管

#### 自建

- 优点：控制力强
- 缺点：维护成本更高

#### 云托管

- 优点：运维成本低
- 缺点：成本与平台绑定更强

#### 推荐

- 如果部署在阿里云且团队运维资源有限，优先考虑托管监控/日志。
- 如果希望环境自包含或便于本地/staging 一致演练，先用 Prometheus + Grafana + Loki。

## 建议门禁

- 代码门禁：
  - 后端 pytest
  - 前端 typecheck / lint / build
  - 新增步骤的专项测试
- 性能门禁：
  - 关键 SLO 不退化
  - 错误率不超阈值
  - 队列长度与资源占用在安全范围内
- 发布门禁：
  - 可灰度
  - 可回滚
  - 有观测看板

## 建议告警

- API 错误率异常
- 登录失败率异常
- 队列积压
- Worker 大量重试
- Redis / PostgreSQL 连接异常
- 外部模型失败率激增

## 实现边界

- 前端：
  - 埋点最小必要信息
- 后端：
  - 暴露 metrics
  - 结构化日志
- 基础设施：
  - dashboard、alert、通知渠道

## 可观测性

- dashboard 至少覆盖：
  - API 延迟
  - API 错误率
  - 队列长度
  - Worker 成功率
  - Redis / PostgreSQL 健康度
  - OSS 上传失败率

## 验收标准

- 有固定压测脚本与报告模板
- 有固定 dashboard 与告警规则
- 以后每一步合并前都能跑同一套检查
