# Step 05：任务状态推送与上传/下载链路卸载

## 标题

把高频轮询和文件中转从 API 进程剥离，降低无效 QPS 与带宽占用。

## 背景

- 当前多个页面用 `setTimeout` 轮询任务状态。
- 当前部分素材上传/下载仍可能经过应用进程。
- 当在线用户升高时，这类“无效状态查询”和“大文件中转”会迅速挤占 API 资源。

## 目标

- 任务状态以 SSE 为主推送
- 轮询改为兜底降级
- 文件上传优先直传 OSS
- 前端静态资源与素材下载优先走 CDN / OSS

## 非目标

- 本步骤不要求引入双向实时协作
- 本步骤不要求删除所有轮询代码

## 方案对比

### 状态推送：SSE vs WebSocket

#### SSE

- 优点：
  - 单向状态推送足够
  - 实现简单
  - 与当前 HTTP 栈兼容性好
  - 运维成本低于 WebSocket

#### WebSocket

- 优点：
  - 支持双向通信
  - 更适合复杂交互
- 缺点：
  - 网关、连接管理、心跳、鉴权复杂度更高

#### 推荐

- **优先 SSE**

### 上传链路：应用中转 vs 直传 OSS

#### 应用中转

- 优点：简单
- 缺点：浪费 API 带宽与磁盘 I/O

#### 签名直传 OSS

- 优点：
  - 显著降低 API 压力
  - 更适合大文件
- 缺点：
  - 前端实现和权限控制更复杂

#### 推荐

- **优先签名直传 OSS**

## 实施粒度（建议）

1. 先为任务状态定义统一事件结构
2. 图片工作室先接 SSE
3. 视频/音频工作室再迁 SSE
4. 保留轮询作为断线重连兜底
5. 再把上传链路切到签名直传
6. 最后把素材访问前置到 CDN/OSS

## 统一事件建议

- `task.created`
- `task.queued`
- `task.started`
- `task.progress`
- `task.asset_ready`
- `task.succeeded`
- `task.failed`

## 实现边界

- 前端：
  - 统一状态订阅 hook
  - 页面不再各自维护独立轮询实现
- API：
  - 提供事件订阅
  - 提供直传签名接口
- Worker：
  - 状态变更时写事件源或状态流

## 可观测性

- SSE 连接数
- SSE 断开率
- 轮询请求量下降比例
- 直传 OSS 成功率
- API 带宽下降比例

## 验收标准

- 至少一个核心工作室页面切到 SSE 主路径
- 任务状态查询 QPS 明显下降
- 至少一种上传场景切为 OSS 直传

- 前端状态订阅规范

## 讨论重点

- 你是否需要后台页面里看到更细的进度事件，而不仅仅是 succeeded/failed？
- 这会影响事件结构设计是否一开始就做得更细。
