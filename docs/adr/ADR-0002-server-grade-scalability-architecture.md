# ADR-0002：采用面向 Linux 服务器的渐进式扩容架构

- **状态**：Proposed
- **日期**：2026-04-19

## 背景

平台当前已经具备多工作室、多模型、多用户隔离与基本生产启动能力，但承载模型仍偏单机应用：

- 状态大量落在 JSON 文件与本地目录
- 会话与任务状态的多 worker 一致性成本高
- 长任务通过 `asyncio.create_task` 挂在 API 进程内
- 前端多个页面依赖轮询查询任务状态
- 静态资源与素材访问部分仍由应用进程直接承载

这套模式适合快速迭代，但不适合作为“1000 在线用户”的长期生产基座。

## 决策问题

在“继续演进现有代码而不是整体重写”的前提下，平台应该采用哪一种扩容路线最合适？

## 备选方案

### 方案 A：继续以文件存储 + 多 Gunicorn worker 为核心

#### 做法

- 提高 Gunicorn worker 数
- 局部缓存热点读
- 继续保留文件存储和进程内任务
- 对轮询做频率优化

#### 优点

- 改动最小
- 交付快
- 对现有代码扰动最小

#### 缺点

- 根瓶颈不变
- 多节点扩容困难
- 文件锁和目录扫描会随数据量持续恶化
- 进程内任务在重启、扩缩容、发布时不稳

#### 结论

- 适合临时缓解，不适合作为 1000 在线目标架构

### 方案 B：Linux 多实例 API + Redis + PostgreSQL + Worker 队列 + OSS/CDN + SSE

#### 做法

- API 节点专注同步请求与任务编排
- Redis 承载会话、缓存、限流、队列
- PostgreSQL 承载核心业务状态与任务索引
- Worker 处理长任务
- OSS/CDN 处理素材
- SSE 优先替代高频轮询

#### 优点

- 与当前代码形态兼容，支持渐进迁移
- 对 1000 在线目标足够现实
- 运维复杂度可控
- 可先单机 Linux，再平滑扩成多节点

#### 缺点

- 需要引入 Redis / PostgreSQL / Worker
- 迁移窗口更长
- 需要补齐压测、监控、数据迁移与回滚策略

#### 结论

- **推荐**

### 方案 C：直接走 Kubernetes + 微服务拆分

#### 做法

- 把工作室、认证、任务、素材等拆成多个服务
- 上 Kubernetes 做编排、扩缩容、服务治理

#### 优点

- 理论扩展性最强
- 便于组织层面按服务拆分

#### 缺点

- 对当前团队与代码基线来说过重
- 首轮改造成本高
- 还没解决“任务模型、数据模型、状态源”的核心问题前，上 K8s 只是放大复杂度

#### 结论

- 适合作为更长期演进方向，不适合作为当前第一阶段目标

## 决策

采用 **方案 B：Linux 多实例 API + Redis + PostgreSQL + Worker 队列 + OSS/CDN + SSE**。

## 关键设计点

### 1. 生产环境假设

- 生产环境为 Linux 服务器
- 推荐优先支持 Ubuntu 22.04+ / Debian 12+ / Alibaba Cloud Linux 3
- 运行形态优先考虑：
  - Docker Compose on Linux
  - 或 systemd 管理容器/进程
- 不把 macOS 开发环境的文件系统、进程管理、路径行为当作生产基线

### 2. 任务系统原则

- 长任务不能继续依赖 API 进程内协程
- API 必须在“提交任务后快速返回”
- Worker 必须支持：
  - 幂等
  - 重试
  - 超时
  - 状态持久化
  - 发布期间不中断已有任务记录

### 3. 状态系统原则

- 会话、缓存、限流：Redis
- 结构化业务状态：PostgreSQL
- 大文件：OSS
- 不再把本地目录视作多实例共享状态源

### 4. 实时状态原则

- 单向任务状态更新优先使用 SSE
- WebSocket 仅在未来确实需要双向控制、协同编辑或更复杂订阅时再引入
- 轮询保留为兼容和异常降级路径

## 为什么这是当前最适合本平台的方案

- 当前代码还是单仓单体应用，直接微服务化收益不如先修状态边界。
- 当前主要长任务都偏 I/O 密集，异步 Worker + 队列比继续加 API worker 更有效。
- 平台已使用 OSS，天然适合把大文件流量从 API 进程中剥离。
- 平台已有多用户隔离语义，迁往 Redis/PostgreSQL 时边界相对清晰。
- 团队需要的是“可一步步合并”的演进路线，而不是一次性重构。

## 结果

### 正面

- 支持多实例一致性
- 支持独立扩容 API 与 Worker
- 支持更可靠的任务编排
- 支持更标准的 Linux 生产部署

### 负面

- 基础设施数量增加
- 本地开发模式需要更清晰地区分“纯本地”和“近生产”模式
- 文档、部署脚本、测试策略都需要同步升级

## 后续约束

- 每个实施步骤必须：
  - 先有 spec / 讨论结论
  - 再有代码改造
  - 再有验证证据
  - 最后单步合并入 `main`
- 不允许在未建立回滚方案前直接删除原有持久化路径
