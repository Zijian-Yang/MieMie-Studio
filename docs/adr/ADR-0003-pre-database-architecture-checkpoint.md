# ADR-0003：数据库阶段前架构检查点

- **状态**：Accepted
- **日期**：2026-06-06

## 背景

`pre` 分支已经完成 Redis + Celery Worker + 独立视频 Worker + aaPanel/Nginx + Cloudflare 入口的主要验证闭环。阶段 5 的 S4/W2 压测显示，当前单机 Compose 在平台侧读流量、状态观察和受控 `preview-payload` 提交上仍有余量；已知尾延迟更多集中在公网/Cloudflare/客户端链路，而不是本机应用直连。

阶段 6 代码治理也已经把视频工作室主页面和创建/编辑弹窗拆到更可维护的边界：

- `VideoStudioPage.tsx` 降至编排页面，数据加载、任务列表、详情弹窗和任务动作已拆分。
- `CapabilityCreateModal.tsx` 已拆出开发者预览、字段标题、参考素材面板、Mask 面板和输入素材选择器。
- 前端 smoke 已覆盖登录、未登录跳转、项目列表、视频工作室空态、文生视频创建、参考素材创建、局部编辑源视频/Mask 面板、任务列表和详情弹窗。

因此，进入数据库阶段前需要先做架构检查点，避免在证据不足时引入 PostgreSQL / SQLite / SSE 带来的备份、迁移、监控和排障成本。

## 决策问题

下一阶段是否应该立即开始数据库迁移？如果开始，最小、安全、可回滚的第一步是什么？

## 当前结论

**进入数据库设计阶段，采用 Compose 内 PostgreSQL 作为最终核心业务状态库。**

数据库实施仍需分阶段推进，不能一次性替换 JSON。第一阶段允许 JSON 继续作为主数据源，并通过 PostgreSQL 影子索引、回填、双写、对账和读切换逐步降低风险。

实施开始前必须满足：

1. PostgreSQL Compose 部署、备份、恢复和 health 门禁先落地。
2. 每个迁移域都有 schema、回填脚本、对账脚本、读切换开关和回滚路径。
3. JSON 过渡窗口内必须保留对账，不允许只写迁移脚本不写对账脚本。
4. 第一批只迁任务索引/任务状态，不直接整体替换所有 JSON 读写。

最终目标是核心业务状态全部进入 PostgreSQL；Redis 继续承担 session/cache/rate limit/Celery broker/result backend，OSS/本地文件继续承担大文件本体。

## 备选方案

### 方案 A：继续 JSON 原子文件存储，补索引和读缓存

适用条件：

- 单机部署仍是主运行形态。
- W2 平台侧读/提交性能继续满足门禁。
- 主要需求是降低热点列表接口扫描成本。

优点：

- 改动最小。
- 备份和回滚路径延续当前文件目录。
- 对现有多用户目录隔离语义最安全。

风险：

- 长期不适合多主机写入。
- 查询能力和运营分析能力弱。

### 方案 B：引入 SQLite 作为单机索引/查询层

适用条件：

- 仍然单机部署，但 JSON 扫描已经成为明确瓶颈。
- 需要比文件索引更强的查询能力，但暂不需要多主机写入。

优点：

- 运维成本低于 PostgreSQL。
- 可作为 JSON 的派生索引层，先不迁移主数据源。

风险：

- 后续迁 PostgreSQL 仍需再设计 schema 和迁移。
- 写入并发、备份和故障处理需要明确边界。

### 方案 C：引入 Compose 内 PostgreSQL 作为核心业务状态源

适用条件：

- 明确要支持跨主机 API 多实例。
- 项目、任务、素材、会话或审计状态需要结构化查询与可靠事务。
- 团队接受数据库备份、迁移、监控和回滚成本。
- 当前部署希望先保持单机 Compose 运维边界。

优点：

- 长期扩展性最好。
- 支持更标准的数据迁移、查询和审计。
- 与 Redis + Worker + SSE 路线匹配。

风险：

- 第一阶段改造面大。
- 需要双写/回填/校验/回滚策略。
- 若没有明确瓶颈证据，容易过早增加复杂度。

## 下一步进入数据库阶段前的准备包

数据库实施开始前必须先补齐：

1. **数据域清单**：用户、项目、任务、素材、会话、配置、审计日志各自是否迁移、是否保留 JSON 兜底。
2. **迁移顺序**：优先迁只读索引还是核心写入路径。
3. **回滚策略**：数据库失败时是否回退 JSON、如何避免双写不一致。
4. **备份与恢复**：本地、服务器、对象存储各自的恢复演练。
5. **性能门禁**：迁移前后必须对比本机入口和公网入口 p95/p99、失败率、日志热点。
6. **SSE 关系**：是否先迁任务状态表，再引入 SSE；不把数据库和 SSE 绑成一次性大改。

## 决策

当前进入数据库阶段的推荐路径是：

1. 先冻结阶段 5/6 证据和当前代码治理状态。
2. 使用 `docs/plans/2026-06-06-postgres-upgrade-optimization-plan.md` 作为 Compose PostgreSQL 升级优化总计划。
3. 第一实施刀先做 PostgreSQL Compose 基础设施和 health 观测。
4. 第一业务迁移域选择视频工作室任务索引/任务状态。
5. 每个域按“schema → 回填 → 双写 → 对账 → 读切换 → PostgreSQL 主写 → JSON 归档”的顺序推进。

## 影响

正面：

- 明确 PostgreSQL 是最终方向，避免 SQLite 中转带来的二次迁移。
- 通过 JSON 过渡、双写和对账保留当前可运行、可验证、可回滚的 pre 基线。
- 为未来多 API 节点共享核心状态打基础。

负面：

- 过渡期存在 JSON 与 PostgreSQL 双写复杂度。
- Compose 内 PostgreSQL 需要新增备份、恢复、监控和容量管理。
- `StudioPage.tsx`、`FramesPage.tsx` 等大页面治理仍需后续继续推进。
