# ADR-0004：自托管服务发行与运维权限边界

- **状态**：Accepted
- **日期**：2026-08-12

## 背景

`pre` 已完成单机 Compose PostgreSQL-only 运行态验证，但 GitHub 交付仍以源码启动和手工 Compose 操作为主。下一阶段目标是让普通用户在单台 Linux 服务器上快速部署、更新和维护平台，同时增加管理员用户治理、数据库备份和通用 Webhook 告警。

需要明确项目负责的服务器边界，以及 Web 管理页面是否可以直接操作 Docker、Git、宿主机定时任务和数据库恢复。

## 决策

采用以下边界：

1. `pre` 作为下一代自托管发行线，完成验收后替代当前 `main`。
2. 项目交付 API、PostgreSQL、Redis、图片/视频/运维 Worker 和调度器，只监听 `127.0.0.1:<port>`。
3. 域名、DNS、HTTPS、Cloudflare、Nginx/Caddy、aaPanel 和防火墙由部署者管理。
4. 第一版不发布公共应用镜像；安装器从固定 Git commit 在目标服务器本地构建。
5. 生产安装使用幂等 `install.sh`，日常高权限维护使用 `miemie` CLI。
6. Web 管理页面负责用户治理、注册策略、备份/OSS/Webhook 配置、立即备份和只读运行状态。
7. Web 进程不获得 Docker socket、Git 写权限、宿主机 root、任意 shell、数据库恢复或永久数据删除能力。
8. 数据库备份和告警由低权限 `worker-ops` 与 scheduler 执行；数据库恢复、代码更新、回滚和卸载保留在 CLI。
9. 新安装默认 PostgreSQL-only，公开注册默认关闭，首位管理员由安装器显式创建。

## 备选方案

### Web 页面直接管理部署

优点是操作集中。缺点是必须给 Web 服务宿主机或 Docker 高权限，远程代码执行、CSRF、越权或依赖漏洞的影响会扩大到整台服务器，因此拒绝。

### 只提供脚本，不建设管理员页面

优点是实现简单。缺点是用户管理、注册策略、备份状态和告警配置需要服务器登录，不满足非技术管理员的日常使用目标，因此拒绝。

### 强制发布公共 Docker 镜像

优点是安装和更新更快。缺点是需要持续维护 registry、多架构构建、不可变标签和供应链签名。当前单仓库单机交付可以先用本地构建满足目标，后续再以真实安装耗时和用户反馈决定是否增加镜像，因此延期。

## 影响

正面：

- 陌生用户获得稳定的一键安装与管理入口。
- 管理员不需要 SSH 即可完成用户治理、备份和告警日常配置。
- Web 服务不掌握宿主机控制权，安全边界清楚。
- 项目不需要承担不同反向代理和证书体系的自动化维护。

负面：

- 首次安装和每次更新需要在服务器本地构建镜像，时间和磁盘开销高于拉取预构建镜像。
- 部署者仍需自行完成反向代理和 HTTPS。
- CLI 与 Web 控制面需要共享明确的数据契约，并分别维护权限和审计。

## 约束

- 安装和更新脚本必须幂等、脱敏、失败即停并保留恢复路径。
- 管理页面不能通过间接接口触发任意宿主机命令。
- 管理员权限必须由后端强制执行。
- 完成首位管理员 bootstrap 后，系统必须保持至少一个有效管理员。
- Web 管理面只能在 Compose 固定挂载的备份根目录内选择安全相对子目录。
- 备份成功必须区分本地成功和异地 OSS 成功。
- 数据库恢复必须先隔离验证并要求显式二次确认。
