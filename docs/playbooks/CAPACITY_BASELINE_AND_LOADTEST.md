# 容量基线与压测手册

## 目的

为平台扩容改造提供统一、可复用、可比较的压测执行方法和结果记录格式。

## 当前确认目标

当前以 **W2** 为正式目标负载：

- 1000 在线用户
- 200~300 活跃操作用户
- 30 个并行任务提交
- 300~500 个正在观察状态的任务

## 原则

- 先验证平台承载，再验证真实供应商链路。
- 同一类对比必须尽量使用同一套场景、同一环境口径、同一统计窗口。
- 不把供应商配额、外部网络波动、真实生成耗时直接混入平台 API 承载结论。
- 压测记录必须能回溯到 Git 版本、部署版本和测试环境。

## staging 分层

### S0：脚本生产模式基线

- Linux 服务器
- 使用 `./run.sh start --prod`
- 用于在 Step 01 之前快速建立第一版基线

### S1：Compose 近生产基线

- Linux 服务器
- 使用 Docker Compose 启动应用侧服务
- 用于 Step 01 完成后复跑相同场景并比较差异

说明：

- S0 与 S1 的结论都有效，但不可混为同一次对比结果。
- 任何“前后对比”必须明确自己属于 S0 还是 S1。

## 压测前必须记录的信息

- 日期时间
- 执行人
- Git 分支与 commit
- `deployment_version`
- 环境类型：S0 / S1
- 服务器规格：CPU / 内存 / 磁盘 / 操作系统
- 当前运行模式：脚本模式 / Compose 模式
- 反向代理类型（如有）
- 是否接入真实供应商
- 是否启用真实 OSS
- 测试账户与测试数据范围

## 场景目录

### 场景 S1：纯读流量

#### 目标

- 建立读接口延迟和错误率基线

#### 请求类型建议

- 登录后项目列表
- 工作室列表 / 详情
- 模型元数据 / 配置读取
- 任务详情读取

#### 观察重点

- P95 / P99 延迟
- 5xx 错误率
- 大量并发读取时的文件 I/O 放大

### 场景 S2：读写混合流量

#### 目标

- 验证常规活跃用户操作下的稳定性

#### 请求类型建议

- 登录
- 项目创建 / 修改
- 角色 / 场景 / 道具 / 工作室配置的增删改查
- 列表刷新与详情查看

#### 观察重点

- 文件写锁竞争
- 读写混合时延迟抖动
- 错误分类是否清晰

### 场景 S3：任务提交 + 状态观察

#### 目标

- 验证任务提交和状态更新链路是否可承载

#### 请求类型建议

- 最多 30 个并行任务提交
- 300~500 个任务状态观察请求
- 当前阶段默认以平台侧排队/状态链路为重点，不要求真实供应商大规模完成生成

#### 观察重点

- 任务提交接口 P95
- 状态可见延迟
- 状态查询 QPS
- 轮询放大效应
- 平台错误与供应商错误的分类

## 供应商相关规则

- 默认不对真实 DashScope 或其他供应商做大规模压力施加。
- 如果本轮确实需要真实调用：
  - 必须单独标记“真实供应商模式”
  - 必须单独记录成本与配额风险
  - 不得把供应商完成总耗时直接作为平台硬门禁

## 最小字段要求

每次压测与对比至少记录：

- `request_id`
- `user_id`
- `task_id`
- `provider_request_id`
- `deployment_version`
- `loadtest_run_id`
- `scenario_name`

建议采集方式：

- 平台请求链路优先从响应头采集：
  - `X-Request-ID`
  - `X-Deployment-Version`
- 业务任务链路继续从响应体或任务详情中补齐：
  - `task_id`
  - `provider_request_id`

## 使用方式

- Step 00：先用这份手册建立第一版记录口径。
- Step 01：在 Compose 路径复跑同一场景。
- Step 02 ~ Step 06：每一步改造前后都至少复用一个相同场景做前后比较。
